# 变更护栏与推送配置（2026-09-26）

这篇文档回答两个问题：

1. **报告上「新增 N · 下线 M」这两个数字，凭什么信？** —— 护栏（`cloud/tariff/change_guard.py`）
2. **真有变化了，怎么送到我手机上？** —— 推送（`cloud/tariff/notify.py`）

> 🔴 **红线：这两件事都不碰数据源。**
> 护栏**不改采集**（不上游接口、不重试、不改请求参数），它只对**已经采到的 diff 结果**做核验；
> 推送**不改快照、不改变更报告**，它只在 `main()` 末尾读一遍汇总。
> 采集逻辑与快照内容保持原样 —— 报告数字变小的原因**全部**记录在本文件第 3 节。

---

## 1. 为什么需要护栏

上游（尤其联通）按**随机子集**返回数据。于是：

> 「本轮没采到这条」与「这条真下架了」**形态完全一致** —— 都表现为「上一轮有、这一轮没有」。

单看 diff 分不出来。唯一能分辨的证据是**条目自带的日期**：

- 下线日还没到 ⇒ 不可能真下架 ⇒ 是这次没采到（**假下架**）
- 上线日早于上一轮基线 ⇒ 不是这轮上的，是之前漏采、这轮补回来的（**补录**）

护栏存在的意义不是「让数字好看」，而是**让数字经得起追问**。
一条错误的下线记录会让人去核对、去打电话，核对完发现是假的 —— 这种事发生两三次，
这个监控就没人看了。

### 1.1 唯一的判据原则

> **判不出来就保留。**

护栏要摘掉的是「**明显是假的**」那一批，不是「拿不准的」那一批。
拿不准的也摘掉，后果是真变化静默消失 —— 而**少报比多报严重得多**：
多报会被人追问，少报**没人会知道**。

这条原则贯穿全部 5 条判据，也是所有「拿不到 X 就退化成什么样」的实现依据
（拿不到上上轮快照 ⇒ 回弹检测**不生效**而不是「按空集合算」；日期解析不出来 ⇒ 保留而不是丢弃）。

## 2. 前后对比（实测，非估算）

用仓库里真实的两天快照跑，**09-24 基线 → 09-25**，四网：

| 网 | 旧口径 新增/下线/变更 | 护栏后 新增/下线/变更 | 差异来自 |
|---|---|---|---|
| 移动 | 5 / 1 / 3 | **4 / 1 / 3** | 补录 1（上线日早于基线） |
| 联通 | 120 / 123 / 81 | **2 / 118 / 81** | 栏目漂移 5 被抵消、在售→停售 110 计为真下架、补录 3 |
| 电信 | 0 / 71 / 0 | 0 / 71 / 0 | 无（本来就没有假的） |
| 广电 | 0 / 0 / 0 | 0 / 0 / 0 | — |

**联通那 120 条「新增」里，真正的业务新增只有 2 条。**

不装护栏时，每天都会报出上百条「新增 + 下线 **同一条资费**」的噪音 —— 因为
身份键里含栏目名，同一条业务换个栏目就被记了两次。

## 3. 六条逐条说明

### ① 逐条日期核验（`REJECT_FUTURE_OFFLINE` / `REJECT_STALE_ONLINE`）

| 现象 | 判据 | 处理 |
|---|---|---|
| 假下架 | 该条 `endDate`（下线日）**≥ 今天** | 不计入下线，计入 `fake_removed` |
| 假新增 | 该条 `startDate` **< 上一轮基线日期** | 不计入新增，计入 `restored`（补录） |
| 日期解析不出 / 字段缺失 | — | **保留**（不猜） |

⚠️ 两个已踩过的边界：

- 假新增必须用**严格小于**（`d < base`）。用 `<=` 会把「基线当天上线**的真新增**」误判成补录。
- 没有上一轮基线日期时（首跑 / 断档），退化为「上线日早于今日 `STALE_ONLINE_DAYS`（默认 2）天以上」
  才算补录 —— 阈值故意保守，宁可少摘。

### ② 身份漂移（`DETECT_RELOCATE`）

**这不是业务变化，是身份键不稳定。**
条目身份键是 `type2|tariffAttr|name`，含**栏目 / 分类号**。同一条资费从 A 栏目挪到 B 栏目，
就被记成「A 下线一条 + B 新增一条」—— 同一条业务被数了两遍。

护栏做法：按**稳定业务编号**（`_reportNo`）把新旧两侧配对起来抵消。

⚠️ 配对有两个实现上的坑（都踩过）：

1. **候选必须限定在 `added` 集合内**。同一编号在库里可能有多条（挂不同栏目），
   若只要求「新库存在这条编号」，会配对到那条**从未变化的副本**上，
   而真正的假新增键留在原地继续冒充新增（正确率只有 4%）。
2. **两侧「是否属于停售桶」必须比较**（见下条）。

### ③ 停售桶是**真实下架**，不是漂移 🔴

**这是本项目与参考项目判据的最大分歧点，单独写清楚。**

联通把「停售」编码成一级分类 `99`「停售套餐」。所以同编号从在售目录挪进停售目录，
**是一条真实的业务下架记录**，不是采集侧抖动。

实测证据（09-24 → 09-25）：

- 115 对编号移动里 **109 对**是「套餐 → 停售套餐」
- 两轮快照里 **没有任何编号同时挂在两个桶里**（跨桶重复 = 0）⇒ 不是桶归属抖动
- 该桶的 `endDate` **几乎都未到期**（110 条里 4 条写着 `2029-12-31`）

⇒ 结论两条：

1. 跨停售桶的移动单独建模为 `state_moved`：`to_stopped` **只算下线**、`from_stopped` **只算新增**，
   且其新键**不得另算「新增」**（否则一条下架记两次）。
2. 这类移动**豁免日期判据** —— 拿 `endDate` 复核会把**真下架全判成假下架**。
   桶归属才是下架证据，日期在这个桶里没有信息量。

> 换句话说：如果照搬参考项目「用日期复核一切下架」的做法，
> 联通的 110 条真下架会被**静默吃掉**。护栏的方向必须是「判不出来就保留」，
> 而不是「一律按日期判」。

### ④ 回弹检测（`DETECT_REBOUND`）

本轮的新增正好是上一轮的下线（增删互换）⇒ 说明基线跳了一下，丢弃本轮、不记变化。

⚠️ 两级判据，缺一不可：

- **身份级**（需上上轮快照）：同一条编号这轮「新增」、上轮「下线」；
- **计数级**（需上一条 history 记录）：只比数量，用于拿不到上上轮快照时兜底。

两个已修的错：

- **必须双向都一致才算回弹**。只匹配一个方向会误判（单方向的 churn 是正常的）。
- **`old2_rows` 为空不构成证据**。空集合比出来的是「整批下线 = 回弹」，
  会**吃掉真实删除**。所以 `if old2_rows:` 非空才走身份级判据。

样本太小也不下结论：低于 `REBOUND_MIN`（默认 3）条不算，重合率低于 `REBOUND_OVERLAP`（默认 0.6）不算。

### ⑤ 结构变更（`REBUILD_ON_SCHEMA`）

**字段结构变了**（我们改了采集字段 / 上游加了字段）⇒ **只重建基线、不通知**。

不这么做的话，改一次采集字段会炸出**上千条**「字段变更」记录，把真变化淹没。

结构签名 `schema_sig()` 只看**参与 diff 的字段里哪些有值**，采样前 800 条，
带 **1% 噪声阈值** —— 否则 `brandwidth` 偶发一条有值就会触发无谓的基线重建。

### ⑥ 降级状态机（`DEGRADE_RATIO` / `DEGRADE_ACCEPT_ROUNDS`）

数据量**单轮**偏低 ⇒ 冻结旧数据（`hold`），计数 +1；
**连续** `DEGRADE_ACCEPT_ROUNDS`（默认 3）轮偏低且非 0 ⇒ 接受新数据、重建基线（`accept`）。

三个要点：

- **计数必须跨轮次持久化入库**（`degrade_state.json`）。放在内存里，「连续 3 轮」会退化成
  「每轮都是第一轮」，护栏等于没有。
- **0 条不接受**（`accept`）。采到 0 条不是「数据变少了」，是采集挂了 —— 接受它等于把整站清空。
- 降级时**页面照旧出**（用冻结的上一版数据），只打 `::warning`，不再直接退出码 2。
  想恢复老行为：`DEGRADE_STRICT=1`。

## 4. 原子写与产物完整性

CI 有 `timeout-minutes: 20`。被 kill 的时候如果正在写快照，会留下**半个文件**，
而下一轮会把这个半个文件当成新基线 —— 症状是「某天开始数字全乱，且再也不会恢复」。

所以：

- **所有落盘走原子写**：写 `<目标>.tmp` → `os.replace()`（同分区 rename，不会出现中间态）
- **页面写入有闸门**：先写 `docs/index.html.new`，校验通过才替换
  （校验项：占位符残留 = 0 / `const NETS=` 存在 / 体积下限）。
  坏页面的表现是**全站白屏**，而标签、标题全都正常 —— 只有这三项能可靠地拦住它
- **产物完整性闸门**：缺产物就**不许提交**（快照 ≥ 4 份、`page/index.html.gz`、
  `history.json`、`docs/index.html` 非空、四网各有快照）
- 清理并警告残留的 `*.tmp` / `*.new`；`.gitignore` 里也一并挡住 ——
  **写了一半的残片绝不能入库**

## 5. 推送配置

### 5.1 通道与凭据表

推送有两个通道：**邮件（SMTP）** 与 **PushPlus（微信）**。
凭据**全部走 Actions Secrets，代码里一个都不出现**。

| 名称 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `PUSHPLUS_TOKEN` | Secret | PushPlus 必填 | 见 5.3 获取方式 |
| `PUSHPLUS_TOPIC` | Secret | 可选 | 群组编码，配了则推给群组 |
| `SMTP_HOST` | Secret | 邮件必填 | 如 `smtp.qq.com` |
| `SMTP_PORT` | Secret | 可选 | 默认 **465** |
| `SMTP_USER` | Secret | 可选 | 留空则**跳过登录**（用于免认证内网中继） |
| `SMTP_PASS` | Secret | 邮件必填 | 多数邮箱是**授权码**，不是登录密码 |
| `SMTP_SSL` | **Variable** | 可选 | 默认 `1`（SSL，配 465）。设 `0` = STARTTLS（配 587） |
| `MAIL_TO` | Secret | 邮件必填 | **多个收件人用逗号分隔** |
| `MAIL_FROM` | Secret | 可选 | 默认取 `SMTP_USER`，再退到 `MAIL_TO` |
| `MAIL_FROM_NAME` | **Variable** | 可选 | 发件人显示名。代码默认 `资费监控`，工作流默认 `河北资费巡检` |
| `NOTIFY` | **Variable** | 可选 | 默认 `1`。设 `0` = **全关推送**（不用改代码） |

> ⚠️ 上表「类型」是准确的：`SMTP_SSL`、`MAIL_FROM_NAME`、`NOTIFY` 在工作流里是
> `vars.*`（普通变量），其余是 `secrets.*`。放进 Secrets 也能用，但改起来要绕一圈。

### 5.2 配置步骤

1. 仓库 **Settings → Secrets and variables → Actions**
2. 按上表加 Secrets（**New repository secret**）与 Variables（**Variables** 页签）
3. 配完先本地验证通道（用同一个 token / 邮箱发一条，**会真的发出去**）：

```bash
# 只看有哪些通道配齐了，不发消息
python cloud/tariff/notify.py --check

# 真发一条自检消息（把上面的环境变量先 export 好）
python cloud/tariff/notify.py --test
```

CI 里只跑 `--check` 与 `--selfcheck`（**都不发消息**），所以：

> 🔴 **一个通道都没配 ⇒ 静默跳过，不算失败。**
> 本地开发、fork 别人仓库跑，都不会因为没配 SMTP 而变红。

### 5.3 PushPlus token 获取

1. 微信扫码登录 <https://www.pushplus.plus/>
2. 「一对一推送」页复制 **token**（32 位）
3. 想要群推：建群组 → 把群组编码填进 `PUSHPLUS_TOPIC`

接口是 `POST https://www.pushplus.plus/send`，`code == 200` 为成功。
⚠️ `code == 900` = **推送频率超限** —— 代码会额外提示「注意『一次变化只推一条』」，
因为这是**能修**的信息，不该只报一句「失败」。

## 6. 推送的行为契约

### 6.1 一次变化只推一条

一轮巡检要跑四网，还可能重跑（定时 + 手动 dispatch + 重试）。
推送若写在各网内部，同一次变化会被推 4 次、重跑再推 1 次 ——
**用户会直接把这个通知静音，然后真变化也看不见了。**

所以：

- 消息在 `main()` **末尾统一汇总成一条**；
- `SELF_NOTIFY=0` 时本脚本完全不推（交给外部编排）——
  这是「同一个变化被两处各推一次」的正解；
- `.notify_state.json` 记**内容指纹**去重。
  🔴 **指纹必须落盘并入库**：CI 每轮都是全新 checkout，
  只在内存里去重**等于没有去重**，而 `workflow_dispatch` 反复重跑是常态。

### 6.2 零变化不推，但**异常态必推**

设 `NOTIFY_ALWAYS=0`（默认）时，四网都没变化 ⇒ 不推。

⚠️ 没有这道闸门时的一个真事故形态：正文首行是 `# 河北四网资费巡检 {日期}`，
**日期每天不同 ⇒ 内容指纹每天都不同 ⇒ 零变化的日子也会照发一条**
（去重对它完全无效，因为「不是同一份内容」）。天天推「无变化」的结果就是被静音。

但**「无变化」不含异常态**。下面这些状态一律照推，哪怕三个数字全是 0：

| 状态 | 含义 |
|---|---|
| `degraded` | 数据量偏低，已冻结上一版 |
| `rebound` | 检测到基线回弹，本轮未记变更 |
| `schema` | 字段结构变更，仅重建基线 |
| `collect-error` | 本轮采集失败，沿用上一版快照 |
| `resync` | 连续偏低后重同步基线 |

理由：它们在正文里与「**本次巡检未记入任何变化**」长得**很像**，
但**需要人看一眼** —— 静默掉它等于把事故藏起来。
正文里必须显式写出「本轮未记变更（原因）」，靠标题的 `_headline` 区分。

> 只有 `baseline`（首版基线）与 `snapshot-fallback`（沿用仓库快照渲染）
> 被归为「安静态」—— 它们只是「本轮还没有可比基线」，属于正常过程，
> 不该因此发一条废话。

### 6.3 通道互不拖累，推送失败绝不影响巡检

- 一个通道失败（token 过期 / SMTP 被拒）**不能让另一个也不发**
- 推送失败**绝不能让整个巡检失败** —— 数据采到了、页面更新了才是主要产物，
  通知只是附加（所有异常吞掉并打 `::warning`）
- **全失败不记指纹** —— 否则修好之后永远推不出去了（指纹已经被写死）

邮件正文发**两份**：纯文本 + HTML。
只发纯文本会在手机上挤成一团，只发 HTML 又会被纯文本客户端判成垃圾。

🔴 HTML 转换是**自己写的最小实现**，刻意**不引入 markdown 库**：
CI 里多一个依赖就多一个断点，而输入是自己拼的、格式完全可控。
**转义先做、再套标签** —— 反过来会把上游资费文案里的 `<` 当标签放进去
（上游文案实测带真 HTML）。

## 7. 开关总表

全部可用环境变量临时关闭，**默认全开**。

> 🔴 关掉任何一条之前先问自己：**你是在排除护栏的干扰，还是在掩盖一个真变化？**

| 变量 | 默认 | 作用 |
|---|---|---|
| `GUARD` | `1` | 总开关。`0` = 完全退回旧口径（故障时用来对比，**不是**日常开关） |
| `REJECT_FUTURE_OFFLINE` | `1` | ① 假下架（下线日还没到） |
| `REJECT_STALE_ONLINE` | `1` | ① 假新增（上线日早于基线 → 补录） |
| `DETECT_RELOCATE` | `1` | ② 身份漂移 |
| `DETECT_REBOUND` | `1` | ③ 回弹检测 |
| `REBUILD_ON_SCHEMA` | `1` | ④ 结构变更只重建基线不通知 |
| `DEGRADE_RATIO` | `0.6` | ⑤ 单轮跌破此比例 ⇒ 冻结旧数据 |
| `DEGRADE_ACCEPT_ROUNDS` | `3` | ⑤ 连续几轮偏低才接受新数据 |
| `DEGRADE_STRICT` | `0` | `1` = 降级时恢复「退出码 2」硬失败（老行为） |
| `STALE_ONLINE_DAYS` | `2` | ① 无基线日期时的兜底阈值 |
| `REBOUND_MIN` | `3` | ③ 回弹判定最少条数（样本太小不下结论） |
| `REBOUND_OVERLAP` | `0.6` | ③ 回弹判定重合率阈值 |
| `NOTIFY` | `1` | 推送总开关，`0` = 全关 |
| `SELF_NOTIFY` | `1` | `0` = 本脚本不推（交给外部编排） |
| `NOTIFY_ALWAYS` | `0` | `1` = 无变化也每天报个平安 |

## 8. 新增入库文件

| 文件 | 内容 | 为什么必须入库 |
|---|---|---|
| `cloud/tariff/degrade_state.json` | 各网的「连续偏低」计数与冻结状态 | 不入库 ⇒ 每轮都从 0 开始 ⇒「连续 3 轮」退化成「每轮都是第一轮」 |
| `cloud/tariff/.notify_state.json` | 已推送内容的指纹列表 | 不入库 ⇒ CI 每轮全新 checkout ⇒ 去重完全失效 ⇒ 重跑就重复推送 |

> ⚠️ 这两个是**状态文件**，不是缓存。删掉它们不会报错，
> 只会静默地让对应护栏失效 —— 所以列进 CI 的提交步骤，也列在这里。

## 9. 自检与阴性对照

改了判据 / 模板 / 适配器**必跑**：

```bash
python -m ruff check --select F821,F822,F823 --isolated --no-cache cloud/tariff/   # 静态名检查
python cloud/tariff/selftest_pipeline.py     # 集成缝自测（网络换桩）
python cloud/tariff/change_guard.py          # 护栏判据自测（纯逻辑、毫秒级）
python cloud/tariff/notify.py --selfcheck    # 推送该不该发（零变化闸门）
python cloud/tariff/notify.py --check        # 通道配没配（不发消息）
```

五支都进 CI，且全部放在**最前面**当闸门 —— 判据坏了不许继续往下跑采集。

### 9.1 为什么会有前两支（2026-09-26 的真实事故）

护栏自测绿、推送自测绿、`py_compile` 过、本机沙箱「全套验证通过」——
推上去 CI **第 8 步（主流程）直接 `NameError`**，后面 12 步全部 skip。

原因：`other_nets()` 漏初始化一个局部变量，而**本机那些自测清一色是函数级的** ——
只调 `net_round` / `diff_round` / `write_page` / `build_html`，
**没有一个走到 `other_nets` 这个集成缝**（它要真联网，于是被默认跳过）。

⇒ 两条规矩：

1. **集成缝必须有自测**，且用**桩替换网络**（`selftest_pipeline.py`）——
   纯 stdlib、毫秒级，所以没有「太慢所以不跑」的借口。
2. **「一跑到就整轮中断」的错交给静态检查**（`ruff F821/F823`）——
   `py_compile` 只查语法，`NameError` 它一个字都不会报。

⚠️ `ruff` 版本**钉死**在 `0.16.9`，且只选 `F821/F822/F823` 而**不是全部 `F`**：
松着写会在某天上游发新版改了规则后突然变红，而红的原因跟我们的代码无关；
那种红最后必然被绕过，闸门等于没有。

### 9.2 覆盖范围

- **静态**：`cloud/tariff/*.py` 全部文件的未定义名 / 先用后赋值
- **集成缝**：`other_nets()` 四个分支（真采到 / 快照兜底 / 采集失败 / 混跑）、
  返回 4 项契约、summary 字段齐、兜底提示带快照日期、
  **采集失败绝不显示成「无变化」**、`_NOTE_CN` 覆盖全部 note 取值
- **护栏**：日期解析（5 种格式 + 3 种垃圾输入）、假下架、假新增、**边界日**、
  无日期保留、身份漂移、**转停售保留为下线**、**停售→在售算新增**、
  **转停售时日期豁免生效**、回弹三项（双向互换 / 单方向不算 / 无上上轮不算）、
  计数级回弹、降级状态机 5 步、结构签名
- **推送**：零变化不推、空输入、有变化要推、**5 种异常态必推**、
  2 种安静态不推、标题三种形态、HTML 转义、纯文本去标记

### 9.3 阴性对照（确认自测真的在验，而不是永远返回绿）

| 破坏方式 | 期望 |
|---|---|
| 把闸门改成「永远推」（`has_change` 恒真） | 推送自测报 5 项失败 |
| 把异常态也算成「不推」（污染 `_QUIET_NOTES`） | 推送自测报 5 项失败 |
| **把 `summaries` 的初始化从 `other_nets` 删掉**（复原本次事故） | 集成缝自测抛同一个 `NameError`，退出码 1 |

## 10. 排错

| 症状 | 先看哪里 |
|---|---|
| 没收到推送 | `python notify.py --check`：通道配齐了吗 / `NOTIFY` 与 `SELF_NOTIFY` 是不是 `0` / 本轮是不是**真的没变化**（零变化不推是设计） |
| 收到「无变化」的推送 | `NOTIFY_ALWAYS` 是不是设成了 `1` |
| 只收到邮件、没收到微信 | PushPlus 侧看 `msg`；`900` = 频率超限 |
| 该推的没推 | 正文里有没有 `#` 首行日期 —— 指纹是「标题 + 正文」一起算的 |
| 某天起数字全乱 | 看有没有 `*.tmp` / `*.new` 残片入库（原子写被绕过） |
| 报告里某网「本轮未记变更」 | 看 `note` 字段与第 6.2 节的状态表；这是**需要人看一眼**的状态 |
| 联通下线数突然多出一批 | 是不是「在售 → 停售」迁移（`state_moved`）—— 那是**真下架**，见第 3 节 ③ |
