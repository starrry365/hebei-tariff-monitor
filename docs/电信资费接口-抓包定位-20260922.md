## 2. ★ 加解密：已完整破解（本节是本次的核心产出）

### 2.1 密钥就明文写在公开 JS 里

页面 HTML（`https://www.189.cn/wapportalweb/rateZone/index.html`）把资产全列了出来，
其中两份是关键：

| 资产 | 作用 |
|---|---|
| `/client/wap/common/js/aes.js` | CryptoJS UMD 打包，**同时含 `mode-ecb` 与 `pad-pkcs7`** |
| `/client/wapportalweb/vue_common/js/conscript.js` | 封装 `encrypt` / `decrypt`，obfuscator 混淆 |

🔴 **这两份是静态资源，直连就能取**（实测 200；§5 那个 412 只拦 HTML 页面本身）：

```
curl -H 'User-Agent: CtClient;13.4.0;Android;16;23113RKC6C' \
     -H 'x-requested-with: com.ct.client' \
     -H 'Referer: https://www.189.cn/wapportalweb/rateZone/index.html' \
     https://www.189.cn/client/wapportalweb/vue_common/js/conscript.js   # → 3327 字节
```

`conscript.js` 是 obfuscator 混淆的（字符串表全是 `\xNN` 转义）。
把转义解开就能读 —— 关键就两行：

```js
function encrypt(word, key) {
  return CryptoJS.AES.encrypt(
    CryptoJS.enc.Utf8.parse(word),
    CryptoJS.enc.Utf8.parse(key || 'telecom_wap_2018'),   // ←★ 就是这里
    { mode: CryptoJS.mode.ECB, padding: CryptoJS.pad.Pkcs7 }
  ).toString();              // 默认 OpenSSL formatter ⇒ 输出 base64
}
```

**★ 结论：**

```
算法 = AES-128-ECB + PKCS7         密钥 = 'telecom_wap_2018'（16 字节）     没有 IV
包体 = Base64( AES_ECB_PKCS7( UTF-8(JSON) ) )
```

> 反混淆前先看字符串表也能猜到八九分：表里直接躺着
> `mode` / `pad` / `enc` / `AES` / `Pkcs7` / **`ECB`** / `Utf8` / `encrypt` / `decrypt`
> —— 连 `ECB` 和 `Pkcs7` 都是明文字符串。

### 2.2 逐字节自证（这一步是分水岭）

拿页面**自己的函数**（Node 里用 `vm` 加载 `aes.js` + `conscript.js`，再调 `decrypt`/`encrypt`）
把三条抓包密文解出来，再用同一密钥**重新加密**，要求与原包体**逐字节相同**：

| 会话 | 动作 | 原包体 | 解开后明文长度 | 重加密结果 |
|---|---|---|---|---|
| #998 | `tariffSectionHome` 分类树 | 216 字符 | 156 字节 | ★ **逐字节相同** |
| #1053 | `tariffSectionHome` 分类树 | 216 字符 | 156 字节 | ★ **逐字节相同** |
| #1055 | `tariffSectionQuery` 列表 | 280 字符 | 192 字节 | ★ **逐字节相同** |

**为什么非要「重加密回原样」而不是「解出可读文本就算成功」**：
拿错密钥 AES 解密**不会报错**，只会吐出乱码；而乱码有时也"看起来像"结构。
只有**重加密回同一串字节**才能排除巧合 —— 三条全中，密钥与算法就钉死了。

再加两条反证（已写进探针自测）：

- 故意用错密钥 `telecom_wap_2019` → **PKCS7 校验立刻失败**（不是解出乱码）；
- 从金标准密文里**反解出 sessionid**，再用新写的 `build_*()` 重造 → 又**逐字节相同**
  （这条同时把"构造口径"钉死了：键顺序、空格都不能错）。

### 2.3 解开后的明文（这是之前只能"猜"的部分）

```json
// 分类树（#998 / #1053）
{"headerInfo": { "functionCode": "tariffSectionHome"},
 "requestContent":{"ticket":"","sessionid":"<32位hex>","provCode":"1000000037"}}

// 列表（#1055）
{"headerInfo": { "functionCode": "tariffSectionQuery"},
 "requestContent":{"sessionid":"<32位hex>","type":1,"provCode":"1000000037",
                   "lable1Id":"69800a2b83bc522f970bd729"}}
```

几点值得记：

- `"headerInfo": { "functionCode"` 里那个**空格是源码原样**（不是排版）。
  ECB 无随机化 ⇒ 明文逐字节决定密文；虽然服务端解析 JSON 会忽略空格，
  但复刻就复刻到底，免得日后拿「密文不一致」当疑点浪费时间。
- **`ticket` 是空串 ⇒ 这个接口不需要登录。**
- `sessionid` 是**客户端持有、在请求里来回传**的（响应里也回同一个值），不是每次新发。
- ⚠️ 明文里的 `provCode=1000000037` 与页面 URL 里的 `provCode=609001` **不是同一个值**
  ⇒ 两者含义不同，哪个才是「省份」**尚未确认**，别当省码写进代码。

### 2.4 ECB 的两个可观察后果（抓包时不用解密就能用）

1. **相同明文前缀 ⇒ 相同密文前缀。** 两条分类树请求的密文**共同前缀 128 个 base64 字符
   = 96 字节 = 6 个整块**；而这 96 字节正好是明文里的
   `…"requestContent":{"ticket":"","sessionid":"` 这一段
   （连 `sessionid":"` 的引号都算进去是 97 字节 ⇒ 前 6 块整块相同，第 7 块才分叉）。
2. **看密文前缀就能判请求动作**：分类树 ↔ 列表的明文共同前缀是 47 字节
   （`…"tariffSection`，下一个字符正是 **H**ome / **Q**uery）⇒ 密文共同 2 个整块
   = 42 个 base64 字符（实测 42 ✓）。

> 换句话说：**分组链模式（CBC/CFB/OFB/GCM）从第 2 块起就会散开**，
> 绝不可能出现「6 个整块逐字节相同」⇒ 只能是无链接分组模式（ECB）。
> 当初正是靠这一点先判出 ECB，才敢笃定"不用找 IV"，把搜索空间砍掉一半。

⚠️ **安全上的话**：ECB + 硬编码密钥 + 无随机化 ⇒ 同一明文永远同一密文，
报文可被直接指纹化比对。这个接口在密码学意义上**不构成保护**。

## 6. 复现前要带的坑

1. 🔴🔴 **大量响应体是 0 字节，别以为接口没数据。**
   `netcore.log` 里有 **189 条** `Chunked body did not terminate properly with 0-sized chunk.`
   ⇒ 一批 **chunked 响应没被完整落盘**。本次真正拿到体的只有 2077 字节（分类树）与
   256 字节（空列表）。**那份真正的资费列表响应很可能已经丢了** ——
   重抓时若还是 0 字节，先解决 Fiddler 的 chunked 落盘问题，而不是怀疑接口。
2. 🔴🔴 **WAF 是「瑞数类」JS 挑战 —— 这是 17:3x 端到端实测的定论，不是猜测。**
   - `GET …/rateZone/index.html` → 412（早已知）
   - **`POST …/tariffSection.do`（API 本身）→ 也是 412**（`build_tree` / `build_query` 都试了）
   - 412 的响应体是 **JS 挑战页**：`<meta id="3etE7dr7M7O6" content="…">` + `$_ts=…`，
     与 HTML 页面同一套挑战脚本
   - **curl（Schannel TLS）同样 412** ⇒ 拦的不是 TLS 指纹，是**挑战脚本没跑**
   ⇒ 那 `EYg4xOZq0mLeS`（跨会话恒定）/ `EYg4xOZq0mLeT`（每请求变）两条"风控 cookie"
   **就是挑战脚本算出来的** —— 这也解释了它们的行为特征（瑞数类方案的标准形态）。
   ⇒ **纯 requests/curl 不可能通过**。要采数据只有两条路：
   真实 WebView 过挑战后调 `fetch()`；或公开公示页 `www.189.cn/jtzfzq`（同一个 WAF）。
3. ⚠️ `x-qd-reqtime` 是**毫秒时间戳**（本次值 `1790064138220` ↔ 抓包时刻 16:02:18）。
   若服务端校验时间窗，本机时钟漂移会成为隐蔽失败源。
4. ⚠️ **备选路线（未验证，但优先级最高）**：电信也有公开的资费公示页
   `https://www.189.cn/jtzfzq`（curl 返回 **412**，与 §5 同一个 WAF）。
   **若能用真实浏览器过掉 412**，这条路可能和广电一样省事（公开页 ⇒ 不用管加密）。
   —— 不过既然 §2 已经把密钥挖出来了，这条路现在只是"万一"。
5. 🔴🔴 **抓包窗口是「滚动」的，证据必须当场落盘。**
   实测：`LiveTraffic` 的 id 区间在**几分钟内**从 `895~1064` 滚到 `1544~3544`，
   电信那批随即**再也拉不到**（成文时想回头补细节已经取不到了，
   幸好当时把三条密文和响应结构抄了下来）。
   ⇒ 抓到关键会话就**立刻**导出，别指望「等会儿再看」。
6. 🔴 **判「某会话在不在」，别信 `apply_filters`，信不过滤的 `get_sessions`。**
   实测在**已经产生 10099 会话**的情况下，用 `Host Contains "10099"` 过滤**仍返回 0**
   —— 是假阴性（过滤器生效有延迟 / 不可靠）；不加过滤的 `get_sessions` 才是准的。
   **这条与具体是哪家运营商无关，是通用工具教训。**
