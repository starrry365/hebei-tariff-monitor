# 电信能不能在云端采？—— 实测：能（2026-09-22）

## 结论先说

**「电信在 GitHub Actions 上采不到」是错的。** 那是一条**推断**（"Runner 上没有浏览器"），
不是实测结论。2026-09-22 在 `ubuntu-latest` 上实测：用 **Xvfb 起有头 Chrome**
（启动项只给 `--remote-debugging-port`，不给 `--enable-automation`），
**瑞数挑战自动通过，884 条 5 个分类逐项采全**。

真正的前提不是「云端不行」，而是「得有浏览器 **+ 得有屏幕**」—— 而这两样
ubuntu runner 都现成有（`/usr/bin/google-chrome` 是镜像自带的，Xvfb 一个 apt 包）。

三个关键读数：

1. **`"wd":false`** —— `navigator.webdriver` 是 false。这正是唯一决定成败的一项：
   本机早先实测过，`true` 会被 WAF 直接 400 空响应（连挑战页都不给）。
   它取决于**启动方式**（不给 `--enable-automation`），与「本地还是云端」无关。
2. **`"t":"资费专区"`、`"ck":894`** —— 挑战过了，拿到了 894 字节的挑战 cookie。
   说明瑞数**没有**把 GitHub Actions 的出口 IP 段拉黑（至少这一次没有）。
3. **5 个分类的 `count` 与实收 `len` 逐项相等** —— 服务端自报的真实条数对得上，
   不是被截断的残页。合计 884 条，与本机采集完全一致。

## 为什么之前会判错

原来写下的理由有两条，逐条看都能发现它站不住：

| 原判断 | 实际问题 |
|---|---|
| 「云端 Runner 没有浏览器」 | ubuntu 镜像**自带** `google-chrome`；没有的是一块**屏幕**，而 Xvfb 就能补上 |
| 「自动化浏览器会被 400」 | 被拒的是 `navigator.webdriver=true` 的浏览器 —— 那是 `--enable-automation` / chromedriver 造成的，**不是云端造成的** |

两条都把「某个具体做法不行」记成了「那个环境不行」。**这是最值得记的一条教训**：
判据要落在**机制**上（`webdriver` 标志位、有没有屏幕），不要落在**场所**上（本地 / 云端）。

## 落地方式

- 采集脚本：`probes/tools/ct_browser/ci_grab.sh`
  （Xvfb → 有头 Chrome → CDP 导航 → 等挑战 → `harvest_hb.js` → 产物自检）
- 接入点：`.github/workflows/tariff-daily.yml` 的「采集电信」步骤，在
  `tariff_monitor.py` **之前**跑。
- 🔴 **该脚本永不非零退出**：电信是「机会性采集」。采不到时
  `tariff_monitor` 自动退回仓库里最新那份快照渲染 —— 页面不会少一网，
  只是电信数据停在上一版，且提示语带快照日期、`::notice::` 标注走了兜底。

## 仍然存在的风险（别当成已经永久解决）

- 瑞数可能调整策略（拉黑机房 IP 段、加大指纹检测强度），**这一次通过不等于永远通过**。
  所以才有快照兜底这条退路，以及校验步骤里「基线早于今天就说出来」的告警。
- Runner 镜像哪天不再自带 Chrome，`ci_grab.sh` 会退到官方 deb 安装；
  装不上也只是发 `::warning::` 然后走兜底，不影响其它三网。
- 每天只在 06:00 跑一次，频率与原来的本机采集一致。
